4(a) Software engineering methods and tools

Software engineering methods

The team took a lightweight Agile-inspired iterative and incremental approach [1, 2], breaking the project into weekly chunks over seven weeks. Once core requirements (Req1) and initial package boundaries (v1 UML) were agreed, features and reports were built in parallel on branches and merged through pull requests, with regular testing to catch bugs early.

MethodPurposeWhy selected (and alternatives rejected)
Agile-inspired iterations [1] Develop game and reports in weekly stages. Allows balance, collision and scope adjustments during coding, unlike strict Waterfall [1] which leaves integration too late.
Role-based allocation [2] Divide clear ownership across 7 members. Lets code, UML and reports run in parallel without diffused responsibility; lighter than full Scrum [3] (daily stand-ups/velocity do not fit clashing student timetables over 6 weeks).
Incremental branches Build core loop before extra events and polish. Gets movement, timer and pause working first on feature branches before merging extra campus events into main.
Continuous testing Check movement, goose AI, items and collisions. Headless domain packages let fast JUnit 5 tests run on every push alongside manual playtesting before Assessment 2 handover.

Development and collaboration tools

Tools were chosen for compatibility with our iterative workflow, permissive licensing (CR_LICENCES), and suitability for a 2D Java 17 campus game (CR_JAVA, CR_EXECUTABLE):

ToolPurposeFitness with our methods
Git & GitHub (+ Actions/Pages) Version control, 3-OS CI builds and website hosting. Supports parallel branches without overwriting work, runs ./gradlew test lwjgl3:jar on Linux/Windows/macOS, and publishes reports to GitHub Pages.
Discord & WhatsApp Calls, channels and quick daily check-ins. Discord supported design/code calls while WhatsApp handled fast daily coordination and deadline reminders.
VS Code & IntelliJ Writing, refactoring and debugging Java 17 code. Provides Java inspections, step debugging, JUnit runners and Git integration.
libGDX 1.14.2 & LWJGL 3 2D rendering, game loop, input and desktop OpenGL. Provides ShapeRenderer, gdx-backend-headless for unit tests, and cross-platform standalone JAR execution under Apache 2.0 / BSD licences.
Gradle 9.8 Wrapper Build automation and fat-JAR packaging. Locks identical dependency versions and --release 17 across all laptops and CI runners.
JUnit 5, JaCoCo & PlantUML Automated unit tests, coverage and text UML. Verifies 88 domain tests (99.4% line coverage); plain-text .puml files diff cleanly in pull requests.

Alternatives considered

Alternative consideredWhat we used insteadWhy the selected option was preferred
Shared zips / single chat GitHub + Discord/WhatsApp Manual folders lose version history; PRs plus chat channels kept code and tasks organised.
Plain text editor (Notepad) VS Code / IntelliJ IDEA IDEs give compile-time checks, refactoring, JUnit runners and debugging.
Unity / Godot libGDX (Java 17) Unity/Godot break CR_JAVA and add heavy scene binaries; libGDX stays lightweight in Java 17.
Manual JARs / Maven Gradle Wrapper Official gdx-liftoff Gradle setup resolves LWJGL natives and builds fat JARs reproducibly.
IDE-only / manual testing LWJGL 3 JAR + JUnit 5 Meets CR_EXECUTABLE outside IDEs and checks domain rules in seconds on every push.
Draw.io / Lucidchart / Jira PlantUML + HTML snapshots Avoids XML diagram merge conflicts and heavy Jira admin overhead for a 6-week project [2].

4(b) Team organisation

The team adopted a role-based work-package approach [2], assigning each of the seven members clear primary responsibilities paired with backup support so every area was covered without single points of failure.

Dawud Kazi Risk Assessment & Mitigation lead (Risk1.pdf), identifying project/product risks, maintaining the risk register and tracking mitigations.

Justification

This structure suited both the team and the project because Assessment 1 requires six linked deliverables over a tight schedule. Assigning one named lead per deliverable avoided the "joint-responsibility trap" noted in the lectures [2] (where two leads assume the other is finishing a section), while pairing programmers (Daniel and Karthik, backed by James on starter/QA) and cross-reviewing reports (Elliott, Soham, Evan and Dawud) kept our bus factor above one.

Daniel and Karthik focused on Java/libGDX implementation and automated tests while Soham, Elliott, James, Dawud and Evan progressed requirements, architecture, planning, risk and the website in parallel once Req1 IDs were agreed. Regular check-ins led by Elliott kept reports aligned with code changes, avoiding both a chief-programmer bottleneck [1] and an unstructured free-for-all.

Evolution of the project plan

In our initial Week 1–2 draft, we expected full gameplay coding to begin immediately in Week 2–3 alongside requirements gathering. After setting up the libGDX starter, we updated the dependencies so T04 (v1 architecture) waited for our customer interview answers (M2), avoiding rework on classes before clarifying hidden-event and goose-crowding rules.

Once the six v1 PlantUML diagrams landed at the end of Week 4 (91a6bc0), focus shifted to movement, campus obstacles, items and hidden events. Keeping domain packages free of OpenGL made coding and JUnit testing faster than estimated in Week 5, letting us pull GitHub Actions CI, the website and four cohesive Assessment 2 items (FR_CAMPUS_THEME, FR_GEESE_BLOCK, FR_GEESE_DISPERSE, FR_WIN_CONDITION) forward so Assessment 1 delivers a complete win/lose loop.

In Week 6 the plan adapted twice: first, we added a side-by-side branch comparison (12 Nov) to merge Karthik's SlipperyPathEvent and LuckyShortcutEvent from his flat prototype (88ede63) cleanly into the layered architecture as HiddenEvent subclasses; second, JAR checks added tasks for --release 17 bytecode (1356ffa) and bundled licence notices (a120eda), leaving the final days dedicated to documentation review and submission checks.
