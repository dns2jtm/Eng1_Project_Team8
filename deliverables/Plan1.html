4(a) Software engineering methods and tools

Software engineering methods

The team took a lightweight Agile-inspired iterative and incremental approach [1, 2] to development, breaking the project down into smaller chunks and developing the game in stages over the seven-week schedule. Once core requirements (Req1) and our initial package boundaries (v1 UML) were agreed, different features and reports were developed in parallel on branches and brought together through pull requests as the game progressed. Regular automated and manual testing was vital to catch bugs early and tune gameplay feel as we went.

MethodPurposeWhy it was selected (and process alternatives rejected)
Agile-inspired iterative stages [1] Developing the game and reports in weekly increments. Allows gameplay balance, collision handling and scope adjustments throughout development rather than freezing everything upfront as in strict Waterfall [1], which leaves integration too late.
Role-based task allocation [2] Dividing clear ownership across the seven group members. Lets code, UML diagrams and reports progress in parallel without two people assuming the other is finishing a task; lighter than full Scrum [3] (daily stand-ups and story-point velocity are impractical across clashing student timetables over 6 weeks).
Incremental feature branches Building a basic playable loop before adding campus buildings, items and hidden events. Gets core movement, timer and pause rules working first before adding extra events and UI polish, avoiding risky big-bang merges on main.
Continuous testing and debugging Checking movement, goose chasing, item ranges, obstacle collisions and timer accuracy. Separating domain logic from OpenGL lets fast JUnit 5 tests run on every push alongside manual playtesting, catching regressions before Assessment 2 handover.

Development and collaboration tools

The team used several software tools and frameworks to develop the game and support collaboration. These were selected based on compatibility with our iterative workflow, licence suitability (CR_LICENCES), and fitness for building a 2D top-down campus game in Java 17 (CR_JAVA).

ToolPurposeWhy it was selected (fitness with our methods)
Git & GitHub (+ Actions / Pages) Sharing code, version history, 3-OS CI builds and hosting the team website. Lets multiple members work on separate branches without overwriting each other's code, runs ./gradlew test lwjgl3:jar automatically on Linux/Windows/macOS, and publishes live test and coverage reports to GitHub Pages.
Discord & WhatsApp Group communication, voice calls and quick daily check-ins. Discord channels and calls supported longer design/code discussions, while our WhatsApp group handled fast day-to-day coordination and deadline reminders.
VS Code & IntelliJ IDEA Writing, refactoring and debugging Java code. Provides Java 17 inspections, step-through debugging, JUnit test runners and Git integration across macOS and Windows.
libGDX 1.14.2 Main 2D game framework for rendering, game loop and input handling. Provides ShapeRenderer, SpriteBatch and gdx-backend-headless for unit testing; its Apache 2.0 licence permits educational and commercial distribution.
LWJGL 3 Desktop OpenGL graphics, windowing and keyboard input backend. Packages native desktop libraries so the game runs as a single standalone JAR (CR_EXECUTABLE) under a permissive BSD-style licence.
Gradle 9.8 Wrapper Build automation, Java 17 target enforcement and fat-JAR packaging. Integrates cleanly with libGDX (gdx-liftoff) and guarantees every team member and CI runner uses identical dependency versions (Apache 2.0).
JUnit 5 & JaCoCo + PlantUML Automated unit testing, coverage tracking and text-based UML diagrams. JUnit 5 + JaCoCo verify 88 domain tests (99.4% domain line coverage); plain-text PlantUML files sit in Git next to Java code so v1 → v2 diffs are easy to review.

Alternatives considered

Other tools and approaches were evaluated at the start of the project, but the options below were rejected in favour of tools that better matched our requirements and workflow:

Alternative consideredWhat we used insteadWhy the selected option was preferred
Sharing zips / one chat stream only GitHub + Discord & WhatsApp Passing folders manually loses change history; combining GitHub PRs with Discord channels and WhatsApp check-ins kept both code history and team messages organised.
Plain text editors (e.g. Notepad) VS Code / IntelliJ IDEA Java IDEs provide compile-time checks, automated refactoring, integrated JUnit runners and interactive debugging.
Unity / Godot libGDX (Java 17) Unity and Godot violate CR_JAVA and add heavy scene-editor files; libGDX gives lightweight 2D rendering directly in Java 17.
Manual JAR dependency management / Maven Gradle Wrapper Gradle's official libGDX setup automatically resolves cross-platform LWJGL natives and builds the runnable fat JAR reproducibly across team laptops.
IDE-only launch / manual playtesting alone LWJGL 3 standalone JAR + JUnit 5 headless suite Markers and players run a standalone JAR outside an IDE (CR_EXECUTABLE), and JUnit 5 tests verify game rules in seconds on every commit (Section 4.6).
Draw.io / Lucidchart / Jira PlantUML in Git + GitHub Issues / weekly HTML snapshots Manual diagramming tools produce noisy XML diffs, and Jira adds heavy setup overhead for a 6-week project [2].

4(b) Team organisation

The team adopted a role-based work-package approach [2], assigning each of the seven members clear primary responsibilities paired with backup support so every deliverable was covered without leaving single points of failure. This helped distribute the workload fairly, maintain organisation across clashing timetable commitments, and make sure everyone understood how their part connected to the rest of the submission.

Justification

This was the right approach for both the team and the project because Assessment 1 requires six linked deliverables (Website, Req1, Arch1, Plan1, Risk1, and Impl1 + Code/JAR) over a short term schedule. Having one clear owner per area avoided the "joint-responsibility trap" noted in the lectures [2] (where two leads assume the other is finishing a section), while pairing programmers (Daniel and Karthik, backed by James on starter/QA) and cross-reviewing reports (Elliott, Soham, Evan and Dawud) kept our bus factor above one.

Daniel and Karthik could concentrate on getting the Java/libGDX implementation and automated tests solid, while Soham, Elliott, James, Dawud and Evan drove requirements, architecture, planning, risk management and website structure in parallel once the Req1 IDs were fixed. Elliott's coordination through regular meetings and group check-ins kept everyone updated on code changes so the written deliverables stayed consistent with the actual game. By contrast, a chief-programmer bottleneck [1] would have overloaded one person in Week 6, and an informal free-for-all would have risked missed report sections or conflicting edits.

Evolution of the project plan

The first step was to clarify the project's requirements, define team roles and set up the repository and Gradle starter. In our initial Week 1–2 draft, we had expected full gameplay coding to start immediately in Week 2–3 alongside requirements gathering. After setting up the libGDX starter, we adjusted the schedule so that T04 (v1 architecture) waited for our customer interview outcomes (M2), avoiding wasted rework on classes before we knew the customer's exact rules on hidden events and goose crowding.

Once the six v1 PlantUML diagrams were committed at the end of Week 4 (91a6bc0), development shifted to core gameplay mechanics (player and goose movement, campus buildings/lake boundaries, items and hidden events). Because keeping the domain classes free of OpenGL made coding and JUnit testing faster than expected in Week 5, we brought CI workflows, the project website and four straightforward Assessment 2 items (named campus locations FR_CAMPUS_THEME, crowding slowdown FR_GEESE_BLOCK, fed geese dispersing FR_GEESE_DISPERSE, and the 8-goose win condition FR_WIN_CONDITION) forward into Assessment 1 so players can complete a full win/lose session.

In Week 6 the plan adapted twice for integration and compliance: first, when Karthik's flat 7-class prototype (88ede63) and Daniel's layered branch needed combining, we added a short comparison step on review/side-by-side (12 Nov) and ported SlipperyPathEvent and LuckyShortcutEvent cleanly as HiddenEvent subclasses; second, JAR checks added explicit tasks for --release 17 bytecode (1356ffa) and embedded third-party licence notices (a120eda). Leaving the final days specifically for report cross-checking, page-limit verification and public GitHub Pages cutover kept the submission calm and consistent.
