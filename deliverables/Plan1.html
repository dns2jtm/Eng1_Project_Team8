4(a) Software engineering methods and tools

Selected software engineering method and justification

We used a lightweight iterative and incremental approach [1, 2] suited to a 7-student team working over a 6-week term schedule, knowing that another team will inherit our code and documentation in Assessment 2:

  • Early requirements and architecture baseline (Weeks 1–4): Before writing the full game screens, we interviewed the customer, agreed the Req1 IDs and committed our initial v1 UML diagrams. Because Assessment 1 marks six linked deliverables and hands them on in Assessment 2, fixing requirement IDs and package boundaries early let members work on code and reports in parallel without clashing.
  • Small feature-branch increments with automated checks (Weeks 4–6): Gameplay features were built in small steps on Git branches and merged through pull requests (.github/pull_request_template.md) checked by JUnit 5 tests and GitHub Actions builds. Balance numbers (goose speed, crowding slowdown, item ranges) were tuned by playing working builds.
  • Keeping docs and code in sync: Whenever classes or events changed, we updated code comments, the v2 PlantUML files and traceability.html together so the reports matched the actual codebase.

Alternative methods considered and rejected:

  • Strict Waterfall [1]: Freezing every design detail before writing any libGDX code was rejected because movement feel, frame timing and scope decisions needed feedback from a playable build, and leaving integration until Week 6 would have been too risky.
  • Full Scrum [1, 3]: Daily stand-ups, a dedicated Scrum Master role and story-point velocity charts were rejected because seven students have different lecture and lab timetables, and six weeks is too short for velocity estimates to settle. Weekly meetings plus Discord updates and GitHub PR reviews kept us coordinated without extra admin.
  • Unplanned code-and-fix prototyping: Coding straight onto main without package boundaries or unit tests was rejected (and showed its limits when we compared our early flat prototype in Week 6) because mixing OpenGL calls with game rules makes testing and Assessment 2 handover much harder.

4(b) Team organisation

Structure and role allocation

Cohort 2, Team 8 is a group of seven second-year students with no formal manager. Following the ENG1 planning lecture [2], we split the project into owned work packages with a backup reviewer on each:

  • One clear lead per deliverable: As noted in the lectures [2], putting two people "jointly in charge" often means each assumes the other is finishing it. Every work package and report therefore had one named lead responsible for seeing it through to submission.
  • Backup contributor / reviewer (bus factor): Relying on only one person creates a risk if someone gets ill or has overlapping coursework deadlines [2]. Each lead was paired with at least one other member who contributed or reviewed via pull requests and shared drafts.
  • Weekly check-ins: We used a weekly catch-up around the ENG1 lab slot plus group chat threads to track progress against our weekly snapshots and check open risks.

Why this setup suited our team and project

  • Suited the team: Members had different levels of prior experience with Java, libGDX and UML, plus different weekly study schedules. Giving clear ownership let the programmers build the game logic and tests while others drafted requirements, planning and risk documents, with PR reviews keeping everyone familiar with the codebase.
  • Suited the project: Assessment 1 has six distinct outputs (url1.txt/Website, Req1, Arch1, Plan1, Risk1, Impl1 + Code/JAR) that could be worked on in parallel once Req1 IDs and the v1 package design were agreed.
  • Alternatives rejected: Routing every task through one chief programmer [1] would have created a bottleneck in Week 6, while an unstructured free-for-all leads to duplicated code and missed report sections.

How our plan changed week by week

We reviewed progress each week and updated the schedule rather than pretending the Week 2 draft never changed (snapshots on planning.html):

  • Weeks 1–2 (Ordering tasks properly): Our first rough plan had architecture and coding starting straight away in Week 2. Once the repo (13 Oct) and libGDX starter (14 Oct) were set up, we realised writing full classes before the customer interview would cause rework, so we made T3.1 (v1 architecture) wait for M2 (interview answers) and kept Week 2–3 code work to Gradle/libGDX setup checks.
  • Weeks 3–4 (Pushing architecture sign-off to 31 Oct): Customer answers about hidden events and goose crowding meant our model needed obstacle collisions and explicit goose states. Finishing M3 (v1 UML commit 91a6bc0) at the end of Week 4 gave us a clearer structure and made Week 5 coding much smoother.
  • Week 5 (Bringing CI, the website and four A2 items forward): Because the domain classes had no OpenGL dependencies, core coding and JUnit tests came together quickly on 5 Nov (commits be45145–df9c195). With spare time in WP5, we set up GitHub Actions CI, the website and four straightforward A2 gameplay items (named campus buildings/lake FR_CAMPUS_THEME, goose crowding slowdown FR_GEESE_BLOCK, full geese flying away FR_GEESE_DISPERSE, and the 8-goose win target FR_WIN_CONDITION) so the A1 build is a complete game from start to finish.
  • Week 6 (Combining prototypes and checking compliance): By 11 Nov we had two code branches: Karthik's base-game prototype on main (88ede63) and Daniel's layered branch on feature/a1-implementation. We added an unplanned comparison task on 12 Nov (review/side-by-side), kept the tested layered packages, and brought across Karthik's SlipperyPathEvent and LuckyShortcutEvent to give four hidden events in total. In the same week, checks on the built JAR prompted commit 1356ffa (setting --release 17 for CR_JAVA) and commit a120eda (shipping THIRD-PARTY-NOTICES.txt and licence files inside the JAR for CR_LICENCES), leaving the final weekend for finishing the five PDFs and packaging.
